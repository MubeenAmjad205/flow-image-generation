# 1. Primary Goal

Build an automation pipeline that can take a production-package DOCX file, extract the relevant image-generation prompts and settings, convert them into a reliable structured JSON format, and then automate Google Flow to generate the required images.

The eventual workflow should roughly be:

```text
DOCX
  ↓
Document parsing / extraction
  ↓
Identify relevant image prompts + metadata
  ↓
Normalize into JSON
  ↓
Validate JSON
  ↓
Authenticate into Google account
  ↓
Open Google Flow
  ↓
Create new project
  ↓
Configure Flow
  ↓
Disable Agent Mode
  ↓
Select Nano Banana
  ↓
Set required aspect ratio
  ↓
Generate images from prompts
  ↓
Wait for generation
  ↓
Detect completion / failures
  ↓
Collect generated images
  ↓
Rename sequentially
  ↓
Package into ZIP / output folder
```

The automation should eventually be **fast, reliable, low-maintenance, and resistant to UI/document changes**.

# 4. DOCX → Structured JSON Pipeline

The attached DOCX is the input source.

We need to extract the image-generation information from the document and convert it into a normalized JSON structure.

However, there is an important challenge:

## The DOCX structure is NOT guaranteed to remain identical.

The documents are generated by an LLM, so future documents may:

- Change headings
- Change section ordering
- Use different formatting
- Add/remove sections
- Use different table structures
- Change wording
- Put prompts in different locations
- Contain extra irrelevant content
- Have inconsistent formatting

Therefore, do NOT design a parser that simply assumes:

```text
Heading X → paragraph Y → table Z
```

We need a more robust extraction strategy.

---

# 5. Research Robust Document Extraction

Investigate multiple approaches:

### Option A — Deterministic parsing

Use libraries/tools such as:

- python-docx
- DOCX XML parsing
- Tables
- Paragraph styles
- Headings
- Text patterns
- Metadata

### Option B — Hybrid extraction

Use deterministic parsing first, then a small/cheap LLM only when the structure is ambiguous.

### Option C — LLM-assisted structured extraction

Convert the DOCX into normalized text/markdown/XML and ask an LLM to identify the relevant fields.

### Option D — RAG / schema-guided extraction

Use a predefined schema and retrieve relevant sections from the document before asking a cheap model to map them into the schema.

Compare these approaches.

The preferred solution should minimize:

- API cost
- Token usage
- Latency
- Hallucinations
- Failure rate
- Dependency on expensive models


# 22. Important Design Principles

The architecture should follow these principles:

### Reliability > speed

Do not sacrifice correctness for small performance improvements.

### Deterministic first

Use normal code/parsing wherever possible.

### LLM only when useful

Do not send entire documents to an LLM unnecessarily.

### Cheap models

Use free/cheap models for extraction tasks whenever their quality is sufficient.

### Minimal tokens

Only send the relevant document sections to the model.

### Schema validation

Never trust LLM output directly.

### Resumability

A failed job should be recoverable.

### Idempotency

Running the same step twice should not unnecessarily duplicate work.

### Observability

Maintain useful logs and state without leaking credentials or sensitive information.

### Human intervention where necessary

If Google requires CAPTCHA/MFA/manual authentication, the system should pause and allow human intervention rather than trying to bypass it.
